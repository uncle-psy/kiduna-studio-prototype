# Framework-Neutral Implementation Sequence

The user explicitly requested a product plan without prescribing Flutter, Flame, or any other application framework. Preserve these contracts in the technology selected by the development team.

## Phase 1 — Semantic spine

Build and test:

- canonical Realm and relationship types
- stable route/anchor manifest
- Source, Avatar, Ally, Actor, Mage, Presence, Wisdom, Connections, and Scene boundaries
- event envelope and lineage
- permission evaluation interface
- fixture data for the three nested Realms

Exit: every target route renders meaningful server/static content, and no access is inferred from nesting.

## Phase 2 — Continuous Studio shell

Build context inspection, Field viewport, persistent Ki panel, active gathering, single input ownership, contextual action tray, focus restoration, responsive stacking, and navigation persistence.

Exit: a keyboard user can move across Realms without losing orientation, Ki draft, or return position.

## Phase 3 — Realm patterns

Build Duna, Fellowship, and child-Realm patterns. Keep Wisdom, Presence, and Connections as separate view/data flows. Add Mage capability inspection and privacy denials.

Exit: nested hierarchy and effective permissions are clear with zero reliance on orbital layout.

## Phase 4 — R&R boundary and gameplay state machine

Scope game tokens inside the R&R content boundary. Implement Great Hall, matching, Cell assembly, 15 gameplay states, reconnection, progressive rules, voice-independent play, and return to Realm.

Exit: the complete demonstration journey works with fixtures and deterministic events.

## Phase 5 — Allies, Actors, voice, automations, resources boundary

Implement capability grants and revocation before service integrations. Treat voice providers, model providers, and wallet/resource systems as replaceable adapters behind product contracts.

Exit: simulated failure of any provider leaves the Source informed and able to recover or continue safely.

## Phase 6 — Proof and hardening

- unit tests for reducers/state machines and permission rules
- contract tests for data/event schemas
- integration tests for route and state restoration
- end-to-end Source journey
- keyboard and screen-reader audit
- latency, offline, stale-data, and duplicate-event simulations
- threat/privacy review for invitations, voice, Actors, Wisdom, and resources

Exit: acceptance evidence is linked from the corresponding Rapid Board story.

## Acceptance walkthrough

1. Enter Kinship Duna as Danny/Moto.
2. Inspect purpose, role, hierarchy, and Mage boundary.
3. Compare Wisdom, Presence, and Connections.
4. Enter Fellowship of Play and inspect its child Realms.
5. Enter Royals & Rogues and observe the scoped visual transition.
6. Preview an invitation and complete a Private Handshake fixture.
7. Set match preferences and inspect why a Cell was proposed.
8. Join the Cell, bring an Ally, inspect an Actor, and use text when voice is unavailable.
9. Complete setup, deal, power, round, counter, showdown, and after-hand states.
10. Return to the Great Hall and parent Realm without losing relational continuity.

At every step verify current location, actor, permission, visibility, event output, failure recovery, and focus.
